# scripts/

Gate scripts, CRUD helpers, and shared libraries for revoy2's governance
mechanisms. For situational "what do I run / what fires when" guidance, see
the `revoy2-procedure` skill (`.claude/skills/revoy2-procedure/SKILL.md`,
generated by `scripts/generate-procedure-tables.mjs` — do not hand-edit its
generated tables).

## Gate design rules

A gate exists to catch a real failure mode without tripping an agent that is
doing the right thing. Three rules, learned from gates that tripped correct
workflows in practice (2026-08-23):

1. **A gate's failure output names the cause and one remedy command.** Not a
   bare "FAIL" with no next step, and not a wall of rationale an agent has to
   read past to find the actual instruction. State what specifically is
   wrong (which branch, which store, which path) and the single command that
   fixes it. Deeper rationale — why the gate is designed this way, why red is
   sometimes the gate's normal state — belongs behind an opt-in flag
   (`--explain`), not in the default path.

2. **A sanctioned remedy must not create a new blocker without saying so.**
   If following a gate's own printed remedy is expected to trip a second
   gate (e.g. recording a disposition here creates an interview obligation
   in `gate:decision-queue`), say that in the first gate's own remedy text.
   An operator who follows the instructions exactly and still gets blocked,
   with no warning, learns to distrust the gate rather than the situation.

3. **Young or worktree-backed state is in-progress, not abandoned.** A gate
   reasoning about branches, worktrees, or other long-lived artifacts must
   distinguish "nobody has looked at this in a long time" from "someone is
   actively using this right now." A branch committed to minutes ago, or
   checked out in a registered `git worktree`, is not evidence of neglect —
   report it as in-progress (listed for visibility) rather than as a
   blocker demanding an immediate disposition.
