# ADR-138: The Knowledge-Base Retrieval Stage Is Unshipped, And What Exists Is Lexical

**Status:** Accepted
**Date:** 2026-08-27
**Authoring Revision:** 19f62d6ae413605527a5660e2536763e42c9623f
**Content ID:** sha256:62803215ac5c6ccc338ded2c88dd98da47305ff5dc568f5ce3689a57de7348b6

## Context

ADR-112 is titled "Knowledge Retrieval Is Semantic" and describes a ranked
retrieval stage computed from local embeddings. That stage does not run. It has
never run, in any configuration, in this repository.

Verified by execution rather than by reading: `loadVendoredEmbeddingPort()`
returns `null`, because no vendored model asset exists in the tree and no build
step produces one. `KnowledgeBase` and `SqliteKbStore` both default their
`embedder` to that loader, so `selectTopK` unconditionally takes its
`fallback_exact_tag` branch and `cosineSimilarity` is never called on a
production path. Every knowledge-base injection silently runs degraded,
signalled only by a `console.warn`. The code is correct and properly tested
through an injected `EmbeddingPort` double; the missing half is a deliverable
nobody shipped.

An attempt to close this by vendoring the asset produced the finding that makes
this ADR necessary. `VENDORED_EMBEDDING_MODEL` names `arbor-kb-local-embed@v1`,
and inspection showed it is not a pretrained model at all: it is a
character-trigram hashing table whose per-trigram vectors are derived by SHA-256
of the trigram's own text. No learned parameters. No training data. Nothing to
license.

A generated asset was produced and probed empirically:

| Pair | Cosine |
|---|---|
| "the car would not start" vs "the automobile failed to ignite" (synonyms, no shared words) | 0.365 |
| "the car would not start" vs "the cat would not start" (one letter, unrelated meaning) | 0.791 |
| "database connection pool" vs "db conn pooling" (same concept, abbreviated) | 0.351 |
| "database connection pool" vs "banana bread recipe" (unrelated) | -0.131 |

A string whose meaning is entirely different scores **more than twice** as
similar as a genuine synonym pair. This is trigram overlap — fuzzy lexical
matching. It is not semantic similarity, and no asset generated by that scheme
can be, because the vectors carry no information about meaning by construction.

The measure is not worthless: it separates unrelated text from related text, and
it would beat exact-tag-only matching for typo tolerance and morphological
variants. But shipping it under ADR-112's name would convert an honest
"unshipped" into a misleading "shipped" — a reader would see `mode: "semantic"`,
a passing test, and a green gate, and conclude the system retrieves by meaning.
That is a worse failure than the current one, because the current one is at
least visible in the `console.warn`.

## Decision

**1. ADR-112's semantic-retrieval claim is superseded as unshipped.** ADR-112
remains Accepted and its text stands as the record of what was decided. This ADR
records that the stage it describes is designed, implemented, tested, and NOT in
service, and that a reader must not infer otherwise from the code's presence.

**2. The vendored asset is rejected, not merely deferred.** Generating a
19,683-entry SHA-256 trigram table and committing it would make
`loadVendoredEmbeddingPort()` succeed and `cosineSimilarity` execute, and would
therefore make the system *claim* semantic retrieval while performing lexical
matching. The rejection is on the naming and the claim, not on the code quality:
the implementation is sound for what it actually computes.

**3. What the existing code is gets named accurately.** `trigramEmbed` and the
`VENDORED_EMBEDDING_MODEL` spec describe a lexical similarity feature. Any
future decision to ship it must rename the capability and the `mode` value it
reports, so that an operator reading a retrieval result learns whether it was
ranked by meaning or by character overlap.

**4. Genuine semantic retrieval, if wanted, is a separate and larger decision.**
It requires a real embedding model — a dependency with size, licence, and
provenance obligations that this repository's near-zero-dependency posture has
so far deliberately avoided. That trade has never been made explicitly, and this
ADR does not make it. It only stops the corpus from implying it already was.

## Consequences

The corpus stops overstating a capability. A reader of ADR-112 now finds the
record that the stage is unshipped, rather than discovering it by executing a
loader and getting `null`.

Knowledge-base retrieval remains exact-tag and recency only, which is the status
quo and is now honestly described. Nothing degrades; something stops pretending.

The `console.warn` on the degraded path stays. It is the only runtime signal a
reader gets, and until the stage ships it should keep firing rather than being
quieted to make logs tidy.

The cost of this decision is that a working, tested lexical-ranking improvement
sits unused behind a name it cannot honestly wear. That is a real loss, and the
remedy is available and cheap: rename it. This ADR deliberately does not do that
renaming, because the operator's decision here was to stop the misleading claim,
and quietly rebranding a capability in the same change would bury a second
decision inside the first.

## Alternatives / Roads not taken

**Vendor the asset and ship it as semantic.** Rejected on the measurements
above. It would have made every relevant gate green while making the system's
claim about itself false — the precise failure mode this repository's governance
exists to prevent, and one it would not have caught, since no gate checks that a
capability does what its name says.

**Vendor it and rename it to lexical in one change.** Considered, and it is
probably the right eventual outcome. Rejected for now because it bundles two
decisions: "stop claiming semantic" and "ship lexical ranking". The first was
decided; the second was not put to the operator, and inferring approval for a
capability change from approval of a documentation correction is exactly the
overreach the interview process exists to prevent.

**Delete the retrieval code.** Rejected: it is correct, tested, and one rename
away from being useful. The defect is the claim, not the implementation.

**Amend ADR-112 in place.** Rejected: an accepted ADR is effectively immutable
here, and editing its claim to match reality would erase the evidence that the
capability was ever believed shipped. Supersession keeps both facts.
