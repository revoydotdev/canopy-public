# ADR-098: An MCP Client Implements The Protocol, Not One Slice Of It

**Status:** Accepted
**Date:** 2026-08-26
**Authoring Revision:** 5afc268fd12b3731abf2ba5b1ca52a3c941f8153
**Content ID:** sha256:d57c5c453fcfc009b0a1c096e3a7317297c9afa7077deee28ce493b5ed28e409

## Context

`packages/arbor-mcp/src/mcp-client/` implements the MCP client used to connect this harness to external MCP servers. The audit's framing — "the client implements only the tools slice" — is partly stale against the current tree and this Context corrects it rather than repeating it as fact. Verified against `mcp-client.ts`, this client already speaks the protocol's *current* revision handshake: `MCP_PREFERRED_PROTOCOL_VERSION` (`packages/arbor-mcp/src/mcp-client/contracts.ts:3`) is `"2026-07-28"`, and that is in fact the MCP specification's current revision — confirmed directly against `modelcontextprotocol.io/specification/versioning`, which states "the current protocol version is 2026-07-28." `connectModern()` (`mcp-client.ts:63-77`) calls the modern `server/discover` RPC this revision defines, falling back to the legacy `initialize` handshake (`connectLegacy`, lines 78-88) for servers on `2025-11-25` or `2025-06-18` (`MCP_SUPPORTED_PROTOCOL_VERSIONS`, `contracts.ts:4-8`). `http-transport.ts` already emits the 2026-07-28 revision's `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` headers (lines 33-40) and handles both `application/json` and `text/event-stream` response bodies. This is a materially more current implementation than "plain HTTP POST" suggests.

What the audit's core finding gets right, verified: this client implements the *tools* slice of the protocol and nothing else. `McpClient` exposes exactly `listTools`/`callTool`; there is no `resources/list`/`resources/read`, no `prompts/list`/`prompts/get`, no sampling, and no elicitation anywhere in `mcp-client/`. `McpConnector`'s `McpServerConfig` (from `@arbor/config`) has no path for a server capability other than tools. This matters more now than the audit brief assumed, because the 2026-07-28 revision changed how server-to-client interactions work: sampling, elicitation, and `roots` are no longer separate JSON-RPC requests a server pushes over an SSE stream — the transport spec (`/specification/2026-07-28/basic/transports/streamable-http`) confirms servers now embed them as `inputRequests` inside an `InputRequiredResult`, and the client resumes the original call with `inputResponses` (the MRTR pattern, SEP-2322). `McpClient.callTool`'s single-shot `rpc.request("tools/call", ...)` (`mcp-client.ts:52-56`) has no branch for a result whose `resultType` is anything but `"complete"` — an `InputRequiredResult` from a server that wants to elicit input mid-call would fail `McpClient`'s own validation (`result.resultType !== "complete"` throws `"invalid or oversized MCP tools/call result"`), not degrade gracefully.

**Sampling needs a different verdict than the audit brief assumed, and this required checking the current spec rather than building from what the audit found.** Verified directly against `modelcontextprotocol.io/specification/2026-07-28/client/sampling`: sampling is deprecated as of protocol revision 2026-07-28 (SEP-2577). The spec's own guidance is "new implementations SHOULD NOT adopt it; existing implementations SHOULD migrate to integrating directly with LLM provider APIs." The audit brief's instruction to give sampling "special governance attention... a capability that must be gated, not merely implemented" was written against an older mental model of the protocol; the live spec text this repository already targets (`MCP_PREFERRED_PROTOCOL_VERSION = "2026-07-28"`) now steers implementers away from building it at all.

Tool namespacing and collision detection are real and confirmed. `McpConnector.connectAll()` (`mcp-connector.ts:64-70`) namespaces every port and drops any tool whose namespaced name collides, recording an `mcp_tool_collision` diagnostic rather than silently shadowing one server's tool with another's.

`listChanged` is parsed only at connect time, confirmed by direct inspection, settling what the audit could not. `mcp-client.ts:111-112`'s `projectCapabilities` reads `tools.listChanged` off the `server/discover`/`initialize` result once, during `connect()`, and stores it in `this.capabilities`. Nothing in `mcp-client.ts` or `mcp-connector.ts` opens a `subscriptions/listen` stream (the 2026-07-28 mechanism for `notifications/tools/list_changed` and other long-lived change notifications) or registers any notification handler at all — `grep -n "notification" mcp-client/json-rpc.ts mcp-client/mcp-client.ts` returns only the client's own outbound `notifications/initialized` and `notifications/cancelled` sends, nothing inbound. A server that advertises `tools.listChanged: true` and later adds or removes a tool produces no effect on this client until the next full reconnect — the capability is recorded but never acted on.

## Decision

**1. Sampling is explicitly not implemented, and this ADR records why rather than leaving the gap unexplained.** Per the 2026-07-28 spec's own deprecation of the feature, this repository does not add `sampling/createMessage` support to `McpClient`. Where a connected MCP server needs an LLM completion, the correct integration point is this harness's own native model adapter (`@arbor/harness`'s existing model-callable surface), invoked directly by the harness the way the spec now recommends for every implementer — not routed through the MCP client as a server-initiated capability. If a future ADR revisits this, it inherits the governance question the audit brief raised (a server asking the client to run inference must be gated, not ambient) but that question is moot while the feature itself is not built.

**2. `McpClient` and the transports are upgraded to handle `InputRequiredResult`/MRTR for the capabilities this ADR does add — `elicitation` and `roots` — without which those capabilities cannot work under the current revision at all.** `callTool`'s result validation (`mcp-client.ts:52-56`) gains a branch: a `resultType: "input_required"` result carrying `inputRequests` is not an error, it is handed back to the caller (`McpConnector`/the tool port) which resolves each request against a new `McpElicitationPort`/`McpRootsPort` contract and retries the original `tools/call` with `inputResponses` attached — mirroring exactly the sequence the spec's own message-flow diagram describes, not a bespoke reinterpretation of it.

**3. `resources` and `prompts` become first-class capabilities on `McpClient`, gated behind explicit per-server configuration the same way `read_only_tools`/`mutating_tools` already gate tool risk.** `McpServerConfig` gains `resources: boolean` and `prompts: boolean` opt-ins; when set, `connectModern`/`connectLegacy` require the server to have declared the corresponding capability in its `server/discover`/`initialize` result (mirroring the existing `if (!plain(result.capabilities.tools)) throw ...` check at `mcp-client.ts:73`/`98`) and `McpClient` gains `listResources`/`readResource`/`listPrompts`/`getPrompt` methods with the same byte-bounding (`MCP_MAX_RESULT_BYTES`, `MCP_MAX_FRAME_BYTES`) and redaction discipline every existing tool-call path already carries.

**4. `listChanged` triggers real re-discovery, closing the gap this ADR settles rather than leaves open.** `McpConnector` opens a `subscriptions/listen` stream per connected server that declared `tools.listChanged: true` (and, once added, `resources.listChanged`/`prompts.listChanged`), and on a `notifications/tools/list_changed` event re-runs `listTools()` for that server and re-namespaces its ports through the existing collision-detection path in `connectAll()` — the same dedup and `mcp_tool_collision` diagnostic, run incrementally instead of only at initial connect.

## Consequences

Servers that rely on elicitation or roots become usable at all under 2026-07-28 — today they are not, because `McpClient` treats any non-`"complete"` result as a protocol violation. A server whose tool catalog changes mid-session (a common pattern for servers that expose dynamically-discovered resources as tools) becomes visible to the model without a full reconnect. The cost: every new capability is another byte-bounded, redaction-aware parsing path in a client whose entire design discipline is bounding and validating everything a remote, less-trusted server sends — `resources`/`prompts` content is exactly the kind of untrusted external text `redact()`/`redactNativeText` already exists to guard, and each addition is new surface for a malformed or hostile server response to probe. `subscriptions/listen`'s long-lived stream is a new connection-lifetime concern this client has not had before — today every MCP interaction is request/response bounded by `MCP_CALL_TIMEOUT_MS`; a listen stream is deliberately unbounded in duration and needs its own idle/reconnect and resource-cleanup story, tied into `McpConnector.close()`'s existing lease-based teardown. This ADR explicitly does not add OAuth-based authorization — the existing `credential_env`-sourced bearer-token model (`McpServerCredentialBroker`) is unchanged, and the incremental-scope-consent, OIDC-discovery machinery the 2026-07-28 changelog added to authorization is out of scope here.

## Alternatives / Roads not taken

**Implement sampling anyway, gated behind the trust-tier/capability-declaration machinery the audit brief called for.** Rejected once the current spec was actually read: building governance for a feature the protocol's own authors are steering implementers away from is effort spent hardening something that is on a deprecation clock. If a concrete operator need for server-initiated inference emerges, the native model adapter route this ADR names is both spec-aligned and already inside this harness's existing governance surface — it does not need a new MCP-specific gate.

**Keep the client tools-only and treat resources/prompts as permanently out of scope.** Rejected: several real MCP servers (the ones this repository's own `packages/arbor-mcp/tests/mcp-client/fake-mcp-server.ts` test fixture and `mcp-connector.test.ts` already model as a class of dependency) expose their primary value through resources or prompts, not tools, and a client that cannot use either is a client that cannot connect to a meaningful fraction of the ecosystem regardless of how well it handles tools.

**Poll `tools/list` periodically instead of opening a `subscriptions/listen` stream.** Rejected: 2026-07-28 removed the earlier revisions' resumable-GET/session model specifically in favor of the listen-stream pattern; polling would be building against a transport shape the spec itself deprecated one revision ago, and would reintroduce the staleness window `listChanged` exists to close, just on a timer instead of never.

## Obligations

### O1 — Tool namespacing and collision detection are real today and are the pattern the new capability additions extend, not invent

`McpConnector.connectAll()` namespaces every server's tools and omits (rather than silently shadowing) any tool whose namespaced name collides with one already registered, recording an `mcp_tool_collision` diagnostic. This is the concrete precedent this ADR's resource/prompt namespacing and incremental re-discovery both build on.

### O2 — `listChanged` now drives live re-discovery over `subscriptions/listen`, closing the gap this obligation recorded

`McpClient.subscribe()` opens a `subscriptions/listen` stream (with an idle-timeout reconnect loop bounded by `MCP_LISTEN_TIMEOUT_MS`) and forwards every notification on it to the caller; `McpConnector.openLiveDiscovery()` opens one per connected server that declared `tools.listChanged`/`resources.listChanged`/`prompts.listChanged`, and `handleListenNotification()` re-runs `listTools()`/`listResources()`/`listPrompts()` and re-namespaces ports through the same `recomputePorts()` dedup path `connectAll()` uses at initial connect, on the matching `notifications/*/list_changed` event. A server's post-connect tool-catalog change is now observable without a full reconnect.

### O3 — Sampling is not implemented, and this is a deliberate decision tied to the 2026-07-28 spec's own deprecation, not an oversight

No `sampling/createMessage` capability exists anywhere in `mcp-client/`; this ADR records that omission as intentional, citing the spec's SEP-2577 deprecation, rather than leaving it to read as an unexplained gap the way the original audit finding framed it.

### O4 — Elicitation becomes usable once `McpClient.callTool`/`readResource`/`getPrompt` handle `InputRequiredResult` instead of rejecting it; roots is not built, correcting this obligation's own premise against the spec actually fetched during implementation

A `tools/call`, `resources/read`, or `prompts/get` result with `resultType: "input_required"` is resolved through the new `McpElicitationPort` and the original call is retried with `inputResponses`/`requestState`, rather than failing `mcp-client.ts`'s prior `result.resultType !== "complete"` check. `McpClient.requestWithInputHandling()`/`resolveInputRequests()` implement this for all three MRTR-eligible requests (`basic/patterns/mrtr`'s Supported Requests table).

Roots is deliberately **not** built, and this obligation's own text was wrong to pair it with elicitation. Fetching `modelcontextprotocol.io/specification/2026-07-28/client/roots` during implementation (per this repository's "read the spec, don't guess" rule) shows Roots carries the same SEP-2577 deprecation notice this ADR's Context section already cites for sampling: "Deprecated ... 2026-07-28 (SEP-2577) ... New implementations SHOULD NOT adopt it." This ADR's Decision section asked for an `McpRootsPort` without checking that page; building one now would repeat, one paragraph later, the exact stale-audit mistake this ADR's Context exists to correct for sampling. Consistent with O3's sampling posture, no `McpRootsPort` was added and this client declares no `roots` client capability, so a spec-conformant `2026-07-28` server will never send a `roots/list` input request to it in the first place (the MCP spec's `basic/patterns/mrtr` page, requirement 7: "Servers MUST NOT send an inputRequests that the client has not declared support for").
