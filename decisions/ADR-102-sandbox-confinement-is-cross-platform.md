# ADR-102: Confinement Is A Cross-Platform Guarantee Or It Is Not A Guarantee

**Status:** Accepted
**Date:** 2026-08-26
**Authoring Revision:** 5afc268fd12b3731abf2ba5b1ca52a3c941f8153
**Content ID:** sha256:7b6b190f58704cd7627d7c0f691a18b06d9f342cb8212da246f533ef2118b099

## Context

`packages/arbor-mcp/src/sandbox/sandbox-broker.ts` implements exactly one OS-confinement mechanism: Linux bubblewrap namespace isolation. `createSandboxBroker` (lines 51-69) resolves a `SandboxConfinementLevel` and, for `os_best_effort`/`os_required`, calls `probeBubblewrapAvailability` (lines 91-101), which returns a diagnostic immediately — before touching the filesystem — whenever `platform !== "linux"`. `bubblewrapArguments` (lines 129-203) is a single, non-abstracted function that constructs a `bwrap` argv: mount namespaces, PID/IPC/UTS unshare, an optional network namespace with `CAP_NET_ADMIN` for loopback-only access, `prlimit` resource caps, and an overlay-backed writable workspace bind. `SandboxBroker` (the interface in `packages/arbor-mcp/src/sandbox/contracts.ts`) is a single-method `run()` contract with one concrete Linux implementation (`BubblewrapSandboxBroker`) and one fallback (`ApplicationValidatedSandboxBroker`, which does only application-level path/workspace validation — the floor every level enforces, per `validateRequest`). This is wired into the tool host at `native-tool-host.ts:437` via `this.sandbox.run(...)` inside `command()`. There is no seccomp syscall filtering layer, no macOS Seatbelt (`sandbox-exec`) backend, and no Windows story at all — `probeBubblewrapAvailability`'s first check (`platform !== "linux"`) is the entire cross-platform behavior today.

The genuine strength the audit found, and this ADR preserves rather than replaces: `os_required` fails closed. `createSandboxBroker` throws `SandboxConfinementUnavailableError` (lines 31-35, 66) when the platform or the bubblewrap probe cannot deliver OS confinement at that level, rather than silently returning an `ApplicationValidatedSandboxBroker` and letting a caller believe it got more isolation than it did. `os_best_effort`, by contrast, degrades honestly — it downgrades and records why (`diagnostic`) rather than failing, which is the correct behavior for that level's stated contract, not a defect. `DEFAULT_SANDBOX_CONFINEMENT_LEVEL` is `os_best_effort`, confirmed at line 27 — `os_required` is opt-in, not the default; the file's own comment at `cli.ts:1596` shows it used deliberately for unattended-campaign composition, not baked in as the harness-wide floor.

OpenAI's Codex CLI, verified against current documentation rather than assumed, takes the shape this ADR's title argues for: platform-native backends behind one policy, not one platform's mechanism standing in for all of them. On macOS, Codex uses Apple's Seatbelt (`sandbox-exec`) with a dynamically generated policy. On Linux, it combines Landlock (kernel ≥5.13, capability-based filesystem access control, no root required) for filesystem confinement with seccomp for syscall-level network blocking (denying `connect`/`bind`/`listen`/`sendto`/`sendmsg` while exempting `AF_UNIX` so local IPC keeps working), via a separate `codex-linux-sandbox` helper process that applies restrictions to its own thread before `execvp`-ing the target command. Where Landlock is unavailable, Codex falls back to bubblewrap — the same mechanism this repository already uses as its only backend. (Simon Willison's investigation and the Codex Knowledge Base's platform-implementation writeup both corroborate this shape; both are third-party analyses, not the vendor's own docs, cited here as the best available verification of current Codex behavior.)

## Decision

**1. `SandboxBroker` becomes a platform-dispatching contract over per-platform backends, not a single Linux implementation with a platform check bolted onto its probe.** `createSandboxBroker` keeps its existing signature and `SandboxConfinementLevel` semantics unchanged, but its internals dispatch on `options.platform ?? process.platform` to select among registered backends: `BubblewrapSandboxBroker` (Linux, unchanged), a new `SeatbeltSandboxBroker` (macOS, wrapping `/usr/bin/sandbox-exec` with a generated `.sb` profile scoped to the same workspace-root/dependency-root/writable-overlay shape `bubblewrapArguments` already encodes), and `ApplicationValidatedSandboxBroker` as the explicit floor on Windows and any platform without a registered OS backend. The `SandboxBroker` interface itself does not change — `run(request: SandboxedCommandRequest): Promise<SandboxedCommandResult>` stays the one method every backend implements — so `native-tool-host.ts:437`'s call site requires no change.

**2. Linux gains a seccomp network-denial layer alongside bubblewrap's namespace isolation, closing the gap Codex's own Linux backend already closes.** Today, `request.network_denied` is enforced by giving the sandboxed process its own empty network namespace (`--unshare-net`) with only loopback brought up — namespace-level denial, not syscall-level. This is a real boundary, but it is one mechanism doing one job; a seccomp filter denying `connect`/`bind`/`listen`/`sendto`/`sendmsg` (with the same `AF_UNIX` exemption Codex uses, since this repository's own `network_denied` path already depends on loopback IPC for test suites) becomes a second, independent layer applied inside the same `bwrap` invocation via `--seccomp`, not a replacement for the namespace unshare.

**3. The degradation ladder is explicit and ordered per platform, and is a property `run()`'s result already carries.** `SandboxedCommandResult.confinement` already distinguishes `"os_confined"` from `"application_validated"` (this is how `os_best_effort`'s honest downgrade is observable today); this ADR adds no new confinement grade, only new *paths* to `"os_confined"` on macOS and a stricter one on Linux. The ladder, per platform: Linux tries bubblewrap+seccomp, degrades to bubblewrap-only if the seccomp filter cannot be installed (recorded as a distinct diagnostic string, not a silent seccomp-less "os_confined"), then to `application_validated`. macOS tries Seatbelt, then `application_validated`. Windows has no OS-backend rung at all — it goes straight to `application_validated`, exactly as every unsupported platform does today, and this ADR does not invent a Windows mechanism it cannot verify.

**4. `os_required` stays fail-closed and stays opt-in, unchanged.** `SandboxConfinementUnavailableError` continues to be thrown from `createSandboxBroker` whenever the resolved platform's registered backend cannot deliver OS confinement — now correctly firing on macOS without a working Seatbelt, not just on any non-Linux platform. `DEFAULT_SANDBOX_CONFINEMENT_LEVEL` remains `os_best_effort`; nothing in this ADR argues for making `os_required` the harness-wide default, because doing so would make every macOS or Windows host with no Seatbelt/no OS backend unable to run a single command until this ADR's macOS work lands and Windows work is separately decided.

## Consequences

A macOS operator gets a real OS-level confinement boundary instead of `ApplicationValidatedSandboxBroker`'s application-level-only floor, and `os_required` becomes meaningful on macOS rather than universally unsatisfiable there. Linux gains defense in depth: a compromised or buggy sandboxed process that finds a way around the namespace-level network denial still has to clear a syscall filter. The cost is real: `bubblewrapArguments` is 75 lines of carefully commented, security-sensitive argv construction, and this decision commits to maintaining an equivalent Seatbelt profile generator with its own edge cases (Seatbelt's `.sb` policy language is not bubblewrap's argv model — the rust-toolchain-context and dependency-root-overlay logic in `bubblewrapArguments` has no direct Seatbelt equivalent and needs its own translation, not a mechanical port). Windows gets nothing beyond what it has today; this ADR is honest that it closes two of three gaps, not three. `os_best_effort` remaining the default means a fresh macOS checkout before this ADR ships still silently runs at `application_validated` — that is the existing, correct behavior for that level, not a regression, but it means the benefit of this ADR is contingent on the Seatbelt backend actually landing, not on the ADR being accepted.

## Alternatives / Roads not taken

**Make `os_required` the default confinement level instead of building per-platform backends.** Rejected: this would not add confinement anywhere it does not already exist — it would only make every non-Linux host (and any Linux host without `/usr/bin/bwrap`) refuse to run commands at all via `SandboxConfinementUnavailableError`. Fail-closed is the right behavior for a caller that explicitly opted into `os_required`; forcing it on every caller by default converts an honest capability gap into an availability outage.

**Adopt a single cross-platform sandboxing library (e.g. a WASM- or gVisor-style userspace kernel) instead of native per-OS mechanisms.** Rejected on the same grounds ADR-090 rejected a universal static-analysis backend: a third-party isolation layer is itself an unaudited trust boundary for a security-sensitive host whose own header comment insists "command execution never uses a shell." Native OS primitives (bubblewrap's namespaces, Seatbelt's MAC policy, Landlock/seccomp) are kernel-enforced and independently auditable; a userspace reimplementation of process isolation is a larger, less-inspectable attack surface to add to exactly the file that exists to shrink attack surface.

**Copy Codex's Linux approach exactly — Landlock plus seccomp instead of bubblewrap plus seccomp.** Rejected for Linux specifically, not because Landlock is worse, but because bubblewrap already gives this repository PID/IPC/UTS/mount namespace isolation and an overlay-backed writable workspace that Landlock's filesystem-only model does not provide on its own; replacing a working, tested backend to match another project's implementation choice would be needless churn. Landlock's advantage — no root and no `bwrap` binary dependency — is real but is a case for *also* supporting Landlock as an additional Linux path in a future ADR, not a case for tearing out bubblewrap now.

## Obligations

### O1 — `os_required` already fails closed on the current single-backend implementation, and this is the property every new backend must preserve

`createSandboxBroker` throws `SandboxConfinementUnavailableError` when `os_required` is requested and OS confinement cannot be delivered, rather than silently returning `ApplicationValidatedSandboxBroker`. This is the concrete, tested behavior this ADR extends to macOS rather than a claim invented for this document.

### O3 — macOS confinement resolves to `os_confined` only when Seatbelt is actually probed and available, never assumed from platform alone

The new `SeatbeltSandboxBroker` path is selected only after a real `sandbox-exec` availability probe (`probeSeatbeltAvailability`, `packages/arbor-mcp/src/sandbox/seatbelt-sandbox-broker.ts`) analogous to `probeBubblewrapAvailability` — `createSandboxBroker` on macOS with no working Seatbelt falls back to `ApplicationValidatedSandboxBroker` exactly as Linux does today without bubblewrap, and `os_required` on such a host still throws (`sandbox-broker.test.ts`'s "ADR-102 platform dispatch" describe block).

**Demonstrates less than it sounds like — say so plainly, per this corpus's house rule.** This obligation's roundtrip test runs on the Linux implementation host, not macOS: it drives `createSandboxBroker({ platform: "darwin", probe_seatbelt_confinement: <injected> })` to verify the *dispatch and fail-closed logic*, and `buildSeatbeltProfile` (a pure function) to verify the *profile text a real run would use*. What it does NOT verify: that `SeatbeltSandboxBroker.run()` actually spawns `/usr/bin/sandbox-exec` correctly, that the generated `.sb` profile is syntactically valid to the real Seatbelt parser, or that Seatbelt actually confines a process the way the profile claims. There is no macOS host in this environment to run any of that. The un-injected `probeSeatbeltAvailability(process.platform, ...)` call in the same test does exercise one real code path — it correctly reports unavailable on this Linux host — but that is the negative case, not the positive one.

### O4 — Linux network denial gains a seccomp layer independent of the existing namespace unshare

`bubblewrapArguments`'s `--unshare-net` namespace-level denial is joined, not replaced, by a seccomp filter (`buildNetworkDenySeccompProgram`, `packages/arbor-mcp/src/sandbox/seccomp.ts`) applied via `--seccomp` inside the same `bwrap` invocation; a request with `network_denied: true` is refused at two independent layers on this host (verified by real execution, not a mock — see below), and the seccomp layer's absence (e.g. an older kernel, or an unimplemented architecture) is recorded as a distinct diagnostic string on the broker (`"...seccomp network-syscall filter unavailable (...)"`) rather than silently reported as identical to a fully layered `os_confined`.

**Narrower than "network syscalls are filtered" — say so plainly.** Classic seccomp-BPF only inspects the scalar register values a syscall was invoked with, never memory a pointer argument refers to. `connect(2)`/`bind(2)` take a `struct sockaddr *`, so the address family is not inspectable from BPF at all, and `listen(2)`/`sendto(2)`/`sendmsg(2)` carry no address-family information on the syscall boundary. A filter keyed on those syscalls could not distinguish loopback traffic (which this repository's own `network_denied` path depends on for local IPC, and which `bubblewrapArguments` itself dials into the sandboxed process tree via `ip link set lo up` to bring `lo` up) from external traffic. The implemented filter instead denies `AF_PACKET` socket *creation* — a scalar, inspectable `socket(2)` argument — closing a real escalation path opened by the `CAP_NET_ADMIN` grant `--unshare-net` requires, while leaving `AF_INET`/`AF_INET6`/`AF_UNIX`/`AF_NETLINK` untouched. `AF_NETLINK` in particular was deliberately NOT added to the denylist after an empirical failure during implementation: denying it broke the sandbox's own `ip link set lo up` step, which needs `AF_NETLINK` and runs inside the same seccomp-covered process tree. The roundtrip test (`sandbox-broker.test.ts`'s "ADR-102 O4" describe block) executes for real on this Linux host — spawning `python3` inside the sandbox and observing `PermissionError` for `AF_PACKET` creation with `network_denied: true`, success without it — this is not a construction-only or mocked proof.
