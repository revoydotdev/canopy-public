# ADR-111: Hooks And Skills Are Operator-Authored, Not A Closed Registry

**Status:** Accepted
**Date:** 2026-08-26
**Authoring Revision:** 5afc268fd12b3731abf2ba5b1ca52a3c941f8153
**Content ID:** sha256:f1caff337e3f3c90f0e315bdddf65c41a3720c12325b2b74319755ba6a789bd6

## Context

`packages/arbor-mcp/src/hooks/` implements this harness's hook system as a fixed, closed handler registry, confirmed directly against `contracts.ts` and `bus.ts`. Every `HookDescriptor` (`contracts.ts:62-72`) carries a `handler_ref` — "names one entry in the closed handler registry (`handlers.ts`); never code-from-disk," per the field's own comment — not a shell command, a script path, or any operator-authored executable. `HOOK_ALL_EVENTS` (`contracts.ts:57`) is the union of three fixed arrays: `HOOK_VETO_EVENTS = ["tool_preflight"]`, `HOOK_OBSERVE_EVENTS = ["tool_audit", "phase", "ledger_transition"]`, and `HOOK_LIFECYCLE_EVENTS = ["session_start", "session_end", "node_start", "node_end", "plan_confirm", "interruption"]` (`contracts.ts:42-44`). Claude Code's `settings.json` hooks, by contrast, let an operator register an arbitrary shell command against events including `UserPromptSubmit`, `PreCompact`, and `Notification` — none of which appear anywhere in this repository's event list, confirmed by direct inspection of `HOOK_ALL_EVENTS`'s three constituent arrays.

The veto-only type design the audit called a genuine strength is real and is proven end-to-end, not merely typed. `HookVetoDecision = { allow: true } | { allow: false; reason: string }` (`contracts.ts:103`) is the only decision shape a veto hook can return; `HookObserveOutcome = { note?: string } | void` (line 116) structurally cannot deny anything — an observe hook has no field in its return type through which it could grant or block. `packages/arbor-mcp/tests/hooks/e2e.test.ts` drives this through `HookBus` and proves `tool_preflight` denial actually stops a tool call, not just that a handler function returns `allow: false` in isolation.

`packages/arbor-mcp/src/skills/catalog.ts`'s `SkillCatalog` is real, bounded, two-phase progressive disclosure, not a stub. `SkillCatalog.fromDirectory` (lines 43-56) loads flat JSON descriptors (`skill_id@version.json`, `SKILL_MAX_DESCRIPTORS` = 64, `SKILL_MAX_DESCRIPTOR_BYTES` = 64 KiB), and `native-tool-host.ts:1082-1108` wires `skill.list` (bounded discovery: id/version/role only) and `skill.load` (full descriptor resolution) as the model-callable two-tool pattern ADR-087 named. What it is not, confirmed by the shape of `SkillDescriptor` (`catalog.ts:14-23`): a `SKILL.md` bundle with nested resource files. The descriptor is one JSON object — `instruction` is a single bounded string (`SKILL_MAX_INSTRUCTION_BYTES` = 16 KiB), `allowed_tools` and `write_path_patterns` are flat string arrays. There is no directory of scripts, templates, or reference files a loaded skill can point the model at the way a Claude Code `SKILL.md` bundle can bundle alongside it.

An operator-authored, arbitrary shell-command hook is, structurally, arbitrary code execution wired into every `tool_preflight` decision this harness makes — a strictly more dangerous admission surface than a new tool port or a new skill descriptor, because a veto hook sits in the path of *every* tool call, not one capability at a time. This repository already has a mechanism built for admitting exactly this class of risk: `packages/arbor-mcp/src/extensibility/plugin-registry.ts`'s `PluginRegistry` requires `verifyPluginManifest(manifest, this.options.trusted_keys)` (lines 75, 112, 157) before installing or upgrading any plugin, and assigns each admitted plugin a `PluginTrustTier` (`"T1" | "T2" | "T3" | "T4"`, `plugin-manifest.ts:4`) with `TIER_REQUIRED_GATES` (line 56) naming what governance gates a given tier must clear. This machinery exists and is signature-verified and tiered today; it is simply not connected to hook authoring at all, because hook authoring does not exist as an operator-facing capability yet.

## Decision

**1. Hooks gain an operator-authored path, but it is admitted through `PluginRegistry`'s signed, tiered trust model — never as a bare `settings.json`-style shell command.** A new `HookHandlerEntry` variant, `{ kind: "plugin"; plugin_id: string; export_name: string }`, lets a `HookDescriptor`'s `handler_ref` resolve to a function exported by an *admitted* plugin (one that has already passed `verifyPluginManifest` and been assigned a tier) instead of only to the closed `handlers.ts` registry. The existing `handler_ref` comment's guarantee — "never code-from-disk" — becomes, precisely, "never code-from-disk outside a plugin's manifest-verified, signature-checked root"; an operator cannot point a hook at an arbitrary unsigned script, only at a function a `PluginRegistry`-admitted plugin exports.

**2. A `tool_preflight` veto hook backed by a plugin requires the plugin's tier to satisfy a new, stricter gate than any other plugin capability this registry admits today.** `TIER_REQUIRED_GATES` (`plugin-manifest.ts:56`) gains a `hook:tool_preflight` entry requiring the highest defined tier (`T4`) — reflecting that a veto hook is not one capability among the plugin's others, it is standing authority over every tool call the harness makes, including ones the plugin itself never registered a tool for. A plugin admitted at a lower tier can still register skills or read-only tool ports; it cannot supply a `tool_preflight` handler until promoted, through the existing `changeTier` mechanism (`plugin-registry.ts:96`), to `T4`.

**3. The closed, built-in `handlers.ts` registry is not removed.** Every hook this repository ships today continues to resolve through it unchanged; this ADR adds a second resolution path for `handler_ref`, it does not migrate existing hooks onto plugin-authored code. `HookVetoDecision`'s two-variant shape and `HookObserveOutcome`'s structurally-grant-incapable shape are unchanged for both paths — a plugin-authored veto hook still can only return `{ allow: true }` or `{ allow: false; reason: string }`, and a plugin-authored observe hook still cannot deny anything through its return type, whatever code backs it.

**4. `HOOK_ALL_EVENTS` gains `user_prompt_submit`, `pre_compact`, and `notification` as new observe-kind events, not veto-kind.** These three events — named for the Claude Code events they parallel — are added to `HOOK_OBSERVE_EVENTS`, never to `HOOK_VETO_EVENTS`. `HOOK_LIFECYCLE_VETO_EVENT` (`contracts.ts:60`) stays exactly `"session_start"`, the one lifecycle event permitted to deny; none of the three new events changes what may or may not veto. This closes the event-parity gap without expanding the set of places a hook can block harness execution.

**5. Skills stay flat, bounded JSON descriptors; a bundle format is explicitly deferred, not built now.** `SkillDescriptor`'s single-instruction, no-nested-resources shape is kept. A `SKILL.md`-with-resources bundle format is real, separable work — it needs its own size/path-escalation model distinct from `SkillCatalogError`'s existing `path_escalation` check on `write_path_patterns` — and bundling it into this ADR would blur a decision about *who may author what* with a separate decision about *what shape a skill's payload takes*.

## Consequences

An operator gets the extensibility Claude Code's `settings.json` hooks provide — react to a prompt submission, react to a context compaction, react to a notification — without this harness's hook system becoming an unaudited arbitrary-code sink. The cost is real and this ADR does not soften it: hook authoring now depends on `PluginRegistry`'s trust-tier machinery being correct, because a bug in tier enforcement or manifest verification is no longer contained to "a plugin's own tools misbehave" — it is "an unverified veto hook can deny every tool call in the harness." Requiring `T4` for `tool_preflight` specifically means the bar for shipping a useful preflight hook plugin is deliberately high, and an operator who wants a quick, low-stakes preflight check pays the same tier cost as one shipping something security-critical — this ADR does not add a lower-cost path for that case, on the judgment that a *veto* hook's blast radius does not have a genuinely low-stakes version. `HOOK_LIFECYCLE_VETO_EVENT` staying fixed to `"session_start"` means none of the three newly-added events can ever gate harness startup or a tool call the way `tool_preflight`/`session_start` can — a plugin author who wants `user_prompt_submit` to be able to *block* a prompt, not just observe it, does not get that from this ADR and would need a separate decision to promote it into `HOOK_VETO_EVENTS`. Skills remaining flat means a skill author who genuinely needs bundled reference material still has to inline it into the one bounded `instruction` string or split it across multiple small skill descriptors — this ADR does not solve that; it names it as deferred.

## Alternatives / Roads not taken

**Let an operator register a bare shell-command hook, matching Claude Code's `settings.json` model exactly.** Rejected: Claude Code's hooks run on the operator's own machine under the operator's own trust boundary; this harness's hooks run inside a governed, sandboxed multi-tenant-adjacent execution model where `tool_preflight` denial is load-bearing for safety properties other parts of the system depend on (the sandbox-broker ADR's confinement guarantees mean nothing if a preflight hook can be swapped for arbitrary unaudited code). Matching Claude Code's model exactly would import its trust assumption along with its convenience, and that assumption does not hold here.

**Require a capability declaration on the hook descriptor instead of routing through `PluginRegistry`'s tier system.** Rejected: a capability declaration the plugin author writes about its own hook is self-attested and unverified — exactly the "documented but not wired" pattern this repository's own conventions warn against. `PluginRegistry` already does signature verification and tier assignment through an external, evidence-backed process (`verifyPluginManifest` against `trusted_keys`, tier promotion/demotion with `evidenceRefs`); reusing it means a hook's admission is backed by the same evidence chain as everything else a plugin does, not a second, weaker parallel one invented for hooks specifically.

**Add `user_prompt_submit`/`pre_compact`/`notification` as veto-capable events to fully match Claude Code's parity.** Rejected for this ADR: `HOOK_LIFECYCLE_VETO_EVENT`'s single-event restriction (`contracts.ts:60`) is itself a documented design decision ("the only lifecycle event a lifecycle hook may ever deny"), and extending veto power to three more events is a separate, larger decision about what may block harness execution — folding it into an event-parity ADR would understate how significant that expansion is.

## Obligations

### O1 — The closed handler registry design is real, and `tool_preflight` denial is proven end-to-end today, not merely typed

`HookBus` drives real hook dispatch, and `packages/arbor-mcp/tests/hooks/e2e.test.ts` proves a `tool_preflight` veto actually stops a tool call through the bus, not just that a handler function in isolation returns `allow: false`. This is the concrete, tested behavior this ADR's plugin-authored veto path must preserve exactly, including the same `HookVetoDecision` two-variant return shape.

### O2 — `PluginRegistry`'s signature-verified, tiered admission model is real today and is the mechanism this ADR routes hook authoring through, not a new parallel trust system

`PluginRegistry` requires `verifyPluginManifest` against `trusted_keys` before installing or upgrading a plugin and assigns each admitted plugin a `PluginTrustTier`; `changeTier` is the existing, evidence-referenced path for promoting or demoting a plugin's tier. This ADR's `T4`-for-`tool_preflight` gate is layered onto this existing, tested mechanism, not invented alongside it.

<!-- proof: symbol=PluginRegistry file=packages/arbor-mcp/src/extensibility/plugin-registry.ts roundtrip=packages/arbor-mcp/tests/extensibility/plugin-registry.test.ts -->

### O3 — A plugin-authored `tool_preflight` hook cannot be admitted below `T4`, and existing built-in hooks are unaffected by the new path

Implemented as a `plugin_tier` check inside `HookCatalog.validateDescriptor` (`catalog.ts`), invoked with the owning plugin's tier from `PluginRegistry.syncComponents` (`plugin-registry.ts`) at every point a plugin's hook components sync (`installComponents`/`enable`/`update`/`rollback`) — the plugin manifest itself carries only component file paths, not parsed hook kind/event, so the gate necessarily lives where the descriptor's `kind`/`event` are actually known, not in `TIER_REQUIRED_GATES` (which is keyed by tier, not capability). A plugin below `T4` that declares a `kind: "veto"` `tool_preflight` hook — or a `kind: "lifecycle"` hook bound to `HOOK_LIFECYCLE_VETO_EVENT` with a deny-capable handler — is refused with a `HookCatalogError("plugin_tier", ...)` thrown out of `installComponents`, not merely warned, and applies uniformly whether `handler_ref` names a `handlers.ts` built-in or a plugin-authored export (`HookHandlerEntry`'s new `"plugin"` kind, resolved via `PluginRegistry`'s `hook_handlers` component + `HookCatalog.addPluginHandlers`). Every hook shipped in `handlers.ts` today continues resolving through the closed registry exactly as before — this obligation is specifically that the new plugin-backed path is additive, never a silent downgrade of an existing hook's trust level.

### O4 — The three added events are observe-kind only; `HOOK_LIFECYCLE_VETO_EVENT` stays exactly `session_start`

`user_prompt_submit`, `pre_compact`, and `notification` are added to `HOOK_OBSERVE_EVENTS`, never to `HOOK_VETO_EVENTS`, and `HOOK_LIFECYCLE_VETO_EVENT` remains `"session_start"` after this ADR lands — no new event gains the power to block a tool call or deny harness startup.
