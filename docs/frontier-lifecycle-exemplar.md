# Frontier lifecycle exemplar

`bun run demo:frontier-lifecycle -- --run-id <id>` is a recorder for a provider-backed Rust campaign through the OpenCode integration. A sealed run complements the Claude-backed TypeScript, Python, and Go generalist package instead of replacing it.

`bun run demo:frontier-codex -- --run-id <id>` drives the same three-turn Rust lifecycle through the Codex CLI integration. This variant requires `codex login status` to pass before capture and routes every clarification and confirmation through literal, timecoded tmux keypresses. Claude Code, OpenCode, and Codex readiness are defined by one closed recorder catalog shared by the publisher and campaign driver, so an integration cannot be accepted by one layer and rejected by the other.

The fixture begins with a failing `cargo test --quiet` suite. Revoy2 plans, delegates, independently reviews, captures, adopts, and verifies the repair. The recorder then adds a checkpoint-continuation requirement to the same repository and submits it through `arbor task follow-up`, preserving campaign lineage while requiring a fresh governed plan, review, adoption, and independent acceptance. Source and evidence publication is a separate `trunk:submit` transaction, not an ad hoc recorder commit/push step.

The publication fails closed unless both starting baselines fail, both adoptions succeed, both independent acceptance runs pass, campaign identities are attributable, media exists, privacy scanning passes, and every checksum reproduces.

Default output is `/mnt/sda2/revoy2/exemplars/frontier-lifecycle/`. Use `--resume` only to retain a previously completed lane after an interrupted recording.

The Codex variant writes beneath `/mnt/sda2/revoy2/exemplars/frontier-codex/` and obeys the same fail-closed publication contract. A successful package is provider- and fixture-specific evidence. It does not establish equivalence between provider models, broad repository parity, or unbounded autonomy.

A sealed exemplar provides fixture-specific evidence for a second integration path, a fourth repository ecosystem, and a multi-turn project lifecycle. It does not establish broad provider parity or claim native conversation replay for connector-owned sessions; terminal resume/fork/respawn remain separately governed by the protected native-session replay contract.
